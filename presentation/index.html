Intro

Hi all,

I started this project because knowledge about Apache Iceberg is not spreading as easily as it should. In short: to get started you need quite a few components. A catalog, object storage, identity, an engine, a place to work. Vendors make that easy, and that is exactly where vendor lock-in begins.

So I built a small platform that shows the other route: every building block open source, running on one laptop with one command. My point today: Iceberg can be a very good choice for autonomy and portability, not only for scale.

The one-liner

What APIs did for applications, Apache Iceberg is doing for data.

For years we have relied on REST and OpenAPI specs to abstract software, so any service can talk to any application. Today Apache Iceberg is doing the exact same thing for structured data: it provides an open and standard interface, including the way you want to run it, so that no single engine owns your data anymore.

01

How Apache Iceberg works

And why it is not a database platform like Snowflake.

01 · Iceberg

A table format, not a product

Snowflake · Databricks · BigQuery
  • One vendor delivers storage, compute, catalog, security and the UI as a single product.
  • Your tables live in the vendor's format and account.
  • You rent the capability. Leaving means migrating data and everything around it.
Apache Iceberg
  • An open specification for how table data and metadata are laid out in object storage.
  • Data files are plain Parquet. Metadata is JSON and Avro. No server owns them.
  • You bring the catalog, the engines, the storage and the identity provider. Each is replaceable.

The comparison is not "which is better". It is "what do you own and what do you rent".

01 · Iceberg

The layers of one Iceberg table

catalogApache Polaris, Iceberg REST. Holds the pointer to the current metadata file per table, plus permissions. This is where a commit becomes atomic.
metadata.jsonSchema with field IDs, partition spec, sort order, properties and the list of snapshots. A new version on every commit; the old one stays.
manifest list .avroOne per snapshot. Lists the manifests of that snapshot with partition statistics, so engines skip whole manifests.
manifest .avroLists data files and delete files with per column min and max, null counts and row counts. This is what makes pruning cheap.
data files .parquetThe actual rows. Immutable. Any engine that speaks Parquet and the Iceberg spec reads them directly from the bucket.

The catalog is tiny. Everything else is files. A commit is the swap of one pointer.

01 · Iceberg

What the format gives you out of the box

  • ACID commits on object storage. Concurrent writers, atomic pointer swap in the catalog.
  • Snapshots and time travel. Every write is a snapshot. Read yesterday's table, roll back a bad load.
  • Schema evolution without rewriting files: add, drop, rename, widen types.
  • Hidden partitioning. Users query on timestamp_utc, Iceberg prunes on day(timestamp_utc).
  • Statistics in metadata. Planning skips files without opening them.
  • Many engines, one copy. DuckDB, Spark, Trino, Flink, PyIceberg. Snowflake and Databricks read Iceberg too.
  • Branches and tags per table for audits and write-audit-publish.
  • Views as first class catalog objects.

In short: the capabilities you associate with a data warehouse, without the warehouse owning your data.

01 · Iceberg

What Iceberg is not

  • Not a query engine. It does not execute SQL. You pick DuckDB, Trino, Spark, Snowflake, or all of them.
  • Not a storage system. It sits on S3 compatible object storage you already have.
  • Not a security layer by itself. Permissions and credential vending live in the catalog and your identity provider.
  • Not maintenance free. Compaction, snapshot expiry and orphan cleanup are yours to schedule.

That is exactly the point. The building blocks are separate, so you decide who owns which one.

02 · Open source

No lock-in: what that means in practice

Data

Parquet files in a bucket you control. Copy the bucket, point another catalog at it, done. No export job, no egress negotiation.

Catalog

Iceberg REST is an open API. Polaris today, another REST catalog tomorrow. Table metadata already lives next to the data.

Engines

DuckDB for a laptop, Trino for a cluster, Snowflake if a team wants it. All read the same table. No second copy.

Lock-in is not one big decision. It is the sum of small defaults. Open formats make every default reversible.

02 · Open source

Autonomy and portability

Autonomy
  • Runs on a laptop, a VM, Kubernetes or a cloud account. Same Compose definition.
  • One command installer for Linux, macOS and Windows. No vendor account, no trial clock.
  • You decide where data lives and which network it ever touches.
  • Costs are compute and storage you already pay for.
Portability
  • Storage: anything with an S3 API.
  • Identity: any OIDC provider. Users and roles stay yours.
  • Catalog: any Iceberg REST implementation.
  • Compute: whichever engine fits the job, per team, per workload.

02 · Open source

PS: the honest part

  • Operations are yours. Upgrades, backups of Postgres and buckets, monitoring, HTTPS, secrets.
  • Table maintenance is yours. Compaction, snapshot expiration, orphan file cleanup need a schedule.
  • Security boundaries are explicit. This build is a local development platform: in-memory sessions, a trusted Docker host. Read the security model before running it anywhere else.
  • Fewer vendors, more decisions. A feature for architecture, a real cost for a small team.

Open source does not mean free of work. What you gain in ownership you also gain in responsibility. My take: worth it when data is a long term asset. It usually is.

The platform

Teams, databases, notebooks. One identity, your own permissions everywhere.

03 · Platform

Architecture

Two Compose projects: iceberg-platform (admin, identity, data services) and iceberg-workspaces (user gateway, notebooks). The gateway restarts independently.
03 · Platform

The capability model

  • Team owns databases. Stable ID, unique name, a description.
  • User signs in with Keycloak, belongs to one or more teams, has one role: read, read and write, admin.
  • Database is an Iceberg catalog in Polaris plus a dedicated S3 bucket. Namespaces, tables and views live inside.
  • Environment per database: development, acceptance, production.
  • Effective access is the union of the user's teams. Moving a database re-syncs grants and bucket policies.
  • No second application database. Polaris is the source of truth for teams, users and catalogs.
  • Portal admin is a Keycloak role. Database admin does not grant portal admin.
  • Self-service for teams, governance in one place.

Ownership is explicit: a team owns a database, a database owns a bucket. That is the whole governance model.

03 · Platform

Security model, in one slide

  • Keycloak issues the token. The user portal, Polaris and notebooks all use that user's token. No shared service account for data access.
  • Polaris vends short lived, table scoped S3 credentials. Notebooks never see bucket root keys.
  • Each notebook session runs in its own container and network: read-only root filesystem, dropped capabilities, CPU and memory limits, no Docker socket.
  • Revoking a membership or deleting a user stops the affected runtimes. Authorization is re-checked every 30 seconds.

Boundaries are documented: this build is for local development. HTTPS, persistent sessions and hostile-tenant isolation are on the list, not in the box.

04

What this means for us

Direction, ownership and three concrete steps.

04 · Wrap up

As far as I'm concerned

  • Iceberg is the storage standard. Whatever engine or vendor we use, tables should land as Iceberg on object storage we own.
  • Catalog and identity are the governance points. Permissions belong in the catalog, users in the identity provider. Not in every tool separately.
  • Engines are replaceable. Treat them as workload decisions, not platform commitments.
  • Self-service with ownership. Teams create and own their databases. The platform team owns the building blocks.
04 · Wrap up

My advice: three concrete steps

  1. Run it. One command, your laptop, twenty minutes. Load a real dataset and query it from two engines.
  2. Decide catalog and identity first. That is where lock-in and governance actually live. Storage and engines follow.
  3. Agree on ownership. Who owns buckets, who owns the catalog, who schedules table maintenance. Write it down before the first production table.

The ambition stays the same: open formats, our data, our choice of tools. This is a working example, not a slide about one.
