Intro

Hi,

Knowledge about Apache Iceberg is not spreading as easily as it should. Before you can start, you need quite a few components: a catalog, object storage, identity, an engine and a place to work. Vendors make that part easy, and that is usually where vendor lock-in starts.

So I built a small platform that shows the other route: every building block open source, running on one laptop with a single command. Apache Iceberg is a very good choice for autonomy and portability.

Intro · How I build

Five principles behind every choice

1 · Clean UXOne Design System. From sign-in to a notebook in a few clicks, one design language in both portals, and a Getting started page in each.
2 · API firstThe portal is just a client. Every button is a documented route with an OpenAPI schema, so a script can do everything a person can.
3 · AI nativeAgents are first-class users. Both portals serve MCP with the user's own identity, data products carry their meaning in a semantic model, and agent skills ship with the installer.
4 · Open sourceNo licences. Every building block is Apache-2.0 or MIT, and so is the platform. No vendor account and no trial clock.
5 · Loosely coupledOpen interfaces between the components. Iceberg REST, S3, OIDC and MCP, so you can replace one block without touching the others. Bigger capabilities come as extensions behind one contract, so the core stays small.
This is the lens for the rest of the talk. Clean UX: team members serve themselves; destructive actions ask for the exact name. API first: the UI has no private backdoor, the OpenAPI schema comes from the same code. AI native: MCP on both portals, tokens issued to the iceberg-mcp client, and agent skills in the Agent Skills format in the installation folder, such as semantic-model, dbt-platform and ingestion. Loosely coupled: every connection between building blocks is an open standard, which is what makes swapping possible. The same idea one level up: Conversational BI, dbt pipelines, Ingestion and OpenMetadata are extensions with their own release, and they reach the core only through the Extension Bridge.
The one-liner

Apache Iceberg is doing for data what open APIs did for applications.

REST and OpenAPI made it possible for any service to talk to any application. Apache Iceberg does the same for structured data: one open table standard, so no single engine owns your data.

01

How Apache Iceberg works

And why it is not a database platform like Snowflake.

01 · Iceberg

Iceberg is a specification, not a product you buy

Snowflake · Databricks · BigQuery
  • One vendor delivers storage, compute, catalog, security and the UI as a single product.
  • Your tables live in the vendor's format and in the vendor's account.
  • You rent the capability, so leaving means migrating the data and everything built around it.
Apache Iceberg
  • An open specification for how table data and metadata are laid out in object storage.
  • Data files are plain Parquet and metadata is JSON and Avro, so no server owns them.
  • You bring the catalog, the engines, the storage and the identity provider, and each one stays replaceable.
01 · Iceberg

Start with what you already know: PostgreSQL

Imagine a simple table: columns, rows and SQL queries.

Who does the job?A regular PostgreSQL tableAn Iceberg table in this platform

and check access		PostgreSQL's system catalogs and permissions.Polaris: the table's name, permissions and current metadata location.
Describe the columnsPostgreSQL's system catalogs.An Iceberg metadata file in object storage.
Store the rowsFiles managed and read by PostgreSQL.Parquet files in a bucket, read directly by the engine.
Scale storage and computeOne server: more data or more queries means a bigger server.Separate: storage grows in the bucket, and each engine brings its own compute.
Compare responsibilities, not identical internals. The last row is the separation of storage and compute: the bucket grows on its own, and DuckDB on a laptop, Spark on a cluster or Snowflake each bring their own compute to the same files. PostgreSQL also stores data in files; applications normally access those files through its server. For an Iceberg query, the engine asks Polaris for the table metadata and access, then reads table files directly from storage. Polaris can read and write Iceberg metadata during catalog operations, but query rows do not flow through it. Even when Polaris uses PostgreSQL as its backing store, that database holds catalog records and permissions; the Iceberg schema and snapshot history live in object storage. Sources: PostgreSQL architecture, PostgreSQL system catalogs, Polaris 1.8.0 entities, Polaris 1.8.0 vended credentials, Polaris 1.8.0 JDBC metastore. Background reading: The Architecture of Apache Polaris, Under the Hood.

02 · Platform · Team workspace

Team administrators run their own databases

No ticket to the platform team: a team administrator creates the catalog and its bucket from the user portal.   • The agent signs in through Keycloak as you: a public client with PKCE, no secret to store.
  • Every call runs with your Polaris grants, so the agent sees exactly what you see and nothing more.
  • The agent never writes SQL: it names metrics, dimensions and filters, and the portal builds the query from the semantic model, so a metric always uses the agreed definition.
  • A shared database stays read-only for the agent too.
  • Destructive tools are marked as such, and the agent is told to ask before using them.
Any MCP client works: Claude Code, Codex, an IDE, or your own agent. The agent reads the model with describe_semantic_model and answers with query_semantic_model, which compiles the agreed metric SQL and runs it read-only with the user's grants. Model Context Protocol over streamable HTTP at /mcp on the user portal. Tokens must be issued to the iceberg-mcp client (azp check), so a browser session token cannot be replayed here. Signature, issuer, audience and expiry are verified and the user is mapped to their Polaris principal on every call. The callback port is fixed so the redirect URI can be exact.
02 · Platform · Extensions

Keep the core small: extensions come in through one Bridge

This is the loosely coupled principle one level up. An LLM chat brings a heavy dependency tree, a model provider and a fast release cycle; none of that belongs in the catalog and identity layer every team depends on. The core stays small: catalog, storage, identity, portals and notebooks. Sources: contracts/bridge/README.md and COMPATIBILITY.md in the core, and the AGENTS.md of the extension. The Bridge capabilities are user-context, automation-principals, automation-tokens, shared-data and listings. OpenMetadata uses only listings: the metadata of the shares a team lists in the data catalog, never a catalog token. An automation principal is a service account for one team in one environment; only that team's administrators create it, and it reaches the data shares the team received through their read role. Its catalog tokens last an hour. Conversational BI asks only for read tokens. dbt pipelines and Ingestion (dlt) write: each run is an isolated container that writes as the team's service account with a short-lived token, and Ingestion keeps pipeline secrets encrypted and write-only. The extension signs people in through its own Keycloak clients, whose tokens Polaris refuses, so a chat session can never be replayed against the catalog. Any producer can describe a table with the table-property conventions, which the catalog shows as Produced by.
02 · Platform · Extensions

Team administrators switch it on, the platform keeps oversight

Enable creates the team's service account for that environment through the Bridge; until then the extension sees nothing of the team. The same works over the extension's MCP server with enable_environment. A revoked service account gets no new tokens, and tokens already issued expire within the hour.
02 · Platform

Security model, in one slide

  • The user portal, Polaris, the notebooks and MCP all work with that user's Keycloak token. No shared service account for data access.
  • Polaris vends short lived, table scoped S3 credentials; notebooks never see bucket root keys.
  • Each notebook session gets its own container and network: read-only root filesystem, dropped capabilities, CPU, memory and process limits, no Docker socket.
  • Revoking a membership stops the affected runtimes within 30 seconds.
  • A data share holds one read grant per table, view or semantic model. A receiving team never gets administration; an external secret is shown once, never stored. A listing in the data catalog publishes metadata only.
  • MCP accepts only tokens issued to the iceberg-mcp client, verified on every call: an agent never holds more than its user.
  • Extensions get no platform secrets or storage keys: a team's service account, enabled by its administrators and revocable by the platform administrator. dbt and Ingestion runs are isolated containers with a short-lived token.

From raw data to answers

A load forecast written in a notebook, given meaning by its contract, shared, listed in a data catalog and asked about in a chat.

03 · Demo · Notebook

A notebook checks the data product, then writes it

The demo product is a synthetic medium-voltage load forecast for network architects: six substations, 48 feeders and 288 assets, a forecast per asset, year and direction from 2026 to 2040, and a precomputed congestion outlook that says when each asset becomes congested and how badly. It is example notebook 09, which every team gets in its notebook workspace. One contract file, grid_forecast.product.yaml, defines the product: the tables, a description for every column, keys, joins, metrics and quality checks. The notebook generates every row, derives the congestion outlook and runs the contract's SQL checks; only when all of them pass does it write the eight Iceberg tables, partitioned by year. The notebook's engine is just an example: any engine with an Iceberg writer works the same way. Polaris checks sander's identity and vends storage credentials scoped to each table. A rerun overwrites the rows of the same tables, so their history and shares survive.
03 · Demo · Semantic model

The meaning, stored beside the tables

↓ AI context and metrics
User portal · semantic model overview with its AI context
User portal · the agreed metrics and relationships
The notebook stores the meaning as an Apache Ossie semantic model in Polaris, in the same namespace as the tables. It comes straight from the contract: every dataset points at its Iceberg table and names its key, every field has a description, a label for its concept and synonyms, the relationships state the joins, and the metrics carry the agreed SQL, such as congestion_points and peak_utilization_pct. The AI context holds what a person would tell a new colleague: the grain, the horizon, the missing-value policy, and never to add up peaks of different assets, because they do not occur at the same moment. The catalog reads the model with the user's own grants, like a table, and draws it. Ossie points a relationship from the many side to the one side; the platform only joins that way, so no row is ever counted twice.
03 · Demo · Data sharing

Share the model with another team, without a copy

A team administrator picks tables, views and semantic models of one database and chooses the recipient: another team, an external party, a listing in the data catalog, or a combination. Selecting a model selects the tables it reads, because a model without its tables cannot be queried. In Polaris a share is one catalog role with one read grant per object, nothing on the namespace or catalog, so a recipient cannot list anything else. A team share is granted to each member's own principal role, including people who join later, and removed when they leave. An external party gets a client ID and a secret shown once. Shares can expire and be revoked at any time; the platform administrator sees every share and can revoke it. There is still only one copy of the data.
03 · Demo · Data catalog

List it in the data catalog, so others find it

↓ a table and a metric up close
OpenMetadata · load_forecast with the model's descriptions, glossary terms and keys
OpenMetadata · the agreed congestion_points metric with its description and dimensions
A listing is the third audience of a data share, next to another team and an external party. It grants nothing: no principal role, no credential, no data. The platform publishes names, column schemas, descriptions and the semantic model through the Extension Bridge's listings capability, never view SQL, storage locations or snapshots. The OpenMetadata extension pushes that to OpenMetadata 2.0 through its REST API: OpenMetadata dropped its own Iceberg connector and never read semantic models, so pulling was not an option. Each listing becomes a data product with its schemas, tables and metrics as assets. The model's datasets and fields become glossary terms, their descriptions land on the tables and columns, its keys become table constraints and an ER diagram, and every metric becomes a Metric entity with its SQL, synonyms and dimensions. Field labels become classification tags. Unlisting, revoking or an expiry removes it within a minute. OpenMetadata is one extension; another data catalog can use the same contract. Someone who finds the product asks grid-planning for a data share.

Wrap up

As far as I'm concerned

  • Iceberg complements platforms like Snowflake. Use it where openness pays off: data that several teams, engines or partners read. Not every table needs to be an Iceberg table.
  • Combining data products is where an integrated platform wins. Joining many data products in one place with good performance is easier when storage, compute and catalog come from one vendor.
  • For Iceberg tables, engines are replaceable. My advice is to treat them as workload decisions, not as platform commitments.
  • Meaning belongs next to the data. A semantic model is part of the data product: owned by the team, checked before it is published, and shared and governed like the tables.
  • Self-service only works with clear ownership. Teams create, own and share their databases, while the platform team owns the building blocks.
  • Agents use the same front door. They get the same identity and grants as the people they work for.
  • Keep the core small, grow through extensions. New capabilities such as Conversational BI, dbt pipelines, Ingestion and OpenMetadata come with their own release, behind one versioned contract.
