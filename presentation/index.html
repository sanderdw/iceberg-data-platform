Intro

Hi,

Knowledge about Apache Iceberg is not spreading as easily as it should. Before you can start, you need quite a few components: a catalog, object storage, identity, an engine and a place to work. Vendors make that part easy, and that is usually where vendor lock-in starts.

Intro · How I build

Five principles behind every choice

1 · Clean UXOne Design System. From sign-in to a notebook in a few clicks, one design language in both portals, and a Getting started page in each.
2 · API firstThe portal is just a client. Every button is a documented route with an OpenAPI schema, so a script can do everything a person can.
3 · AI nativeAgents are first-class users. Both portals serve MCP with the user's own identity, data products carry their meaning in a semantic model, and agent skills ship with the installer.
4 · Open sourceNo licences. Every building block is Apache-2.0 or MIT, and so is the platform. No vendor account and no trial clock.
5 · Loosely coupledOpen interfaces between the components. Iceberg REST, S3, OIDC and MCP, so you can replace one block without touching the others. Bigger capabilities come as extensions behind one contract, so the core stays small.
This is the lens for the rest of the talk. Clean UX: team members serve themselves; destructive actions ask for the exact name. API first: the UI has no private backdoor, the OpenAPI schema comes from the same code. AI native: MCP on both portals, tokens issued to the iceberg-mcp client, and two skills in the Agent Skills format in the installation folder. Loosely coupled: every connection between building blocks is an open standard, which is what makes swapping possible. The same idea one level up: Conversational BI is an extension with its own release, and it reaches the core only through the Extension Bridge.
The one-liner

Apache Iceberg is doing for data what open APIs did for applications.

REST and OpenAPI made it possible for any service to talk to any application. Apache Iceberg does the same for structured data: one open table standard, so no single engine owns your data.

01

How Apache Iceberg works

And why it is not a database platform like Snowflake.

01 · Iceberg

Iceberg is a specification, not a product you buy

Snowflake · Databricks · BigQuery
  • One vendor delivers storage, compute, catalog, security and the UI as a single product.
  • Your tables live in the vendor's format and in the vendor's account.
  • You rent the capability, so leaving means migrating the data and everything built around it.
Apache Iceberg
  • An open specification for how table data and metadata are laid out in object storage.
  • Data files are plain Parquet and metadata is JSON and Avro, so no server owns them.
  • You bring the catalog, the engines, the storage and the identity provider, and each one stays replaceable.
01 · Iceberg

Start with what you already know: PostgreSQL

Imagine a simple table: columns, rows and SQL queries.

Who does the job?A regular PostgreSQL tableAn Iceberg table in this platform

and check access		PostgreSQL's system catalogs and permissions.Polaris: the table's name, permissions and current metadata location.
Describe the columnsPostgreSQL's system catalogs.An Iceberg metadata file in object storage.
Store the rowsFiles managed and read by PostgreSQL.Parquet files in a bucket, read directly by the engine.
Scale storage and computeOne server: more data or more queries means a bigger server.Separate: storage grows in the bucket, and each engine brings its own compute.
Compare responsibilities, not identical internals. The last row is the separation of storage and compute: the bucket grows on its own, and DuckDB on a laptop, Spark on a cluster or Snowflake each bring their own compute to the same files. PostgreSQL also stores data in files; applications normally access those files through its server. For an Iceberg query, the engine asks Polaris for the table metadata and access, then reads table files directly from storage. Polaris can read and write Iceberg metadata during catalog operations, but query rows do not flow through it. Even when Polaris uses PostgreSQL as its backing store, that database holds catalog records and permissions; the Iceberg schema and snapshot history live in object storage. Sources: PostgreSQL architecture, PostgreSQL system catalogs, Polaris 1.8.0 entities, Polaris 1.8.0 vended credentials, Polaris 1.8.0 JDBC metastore. Background reading: The Architecture of Apache Polaris, Under the Hood.

02 · Platform · Extensions

Keep the core small: extensions come in through one Bridge

Big capabilities never land in the core · an extension has its own Compose project and release · it refuses to start outside its contract range, >=0.1,<0.2
This is the loosely coupled principle one level up. An LLM chat brings a heavy dependency tree, a model provider and a fast release cycle; none of that belongs in the catalog and identity layer every team depends on. The core stays small: catalog, storage, identity, portals and notebooks. Sources: contracts/bridge/README.md and COMPATIBILITY.md in the core, and the AGENTS.md of the extension. The Bridge capabilities are user-context, automation-principals, automation-tokens and shared-data. An automation principal is a service account for one team in one environment; only that team's administrators create it, and it reaches the data shares the team received through their read role. Its catalog tokens last an hour. Conversational BI asks only for read tokens. The extension signs people in through its own Keycloak clients, whose tokens Polaris refuses, so a chat session can never be replayed against the catalog. Any producer can describe a table with the table-property conventions, which the catalog shows as Produced by.
02 · Platform · Extensions

Team administrators switch it on, the platform keeps oversight

Conversational BI · mila enables it for grid-planning, one environment at a timeAdmin portal · Teams · every extension service account, who enabled it and when · revoke
Enable creates the team's service account for that environment through the Bridge; until then the extension sees nothing of the team. The same works over the extension's MCP server with enable_environment. A revoked service account gets no new tokens, and tokens already issued expire within the hour.
02 · Platform

Security model, in one slide

  • The user portal, Polaris, the notebooks and MCP all work with that user's Keycloak token. No shared service account for data access.
  • Polaris vends short lived, table scoped S3 credentials; notebooks never see bucket root keys.
  • Each notebook session gets its own container and network: read-only root filesystem, dropped capabilities, CPU, memory and process limits, no Docker socket.
  • Revoking a membership stops the affected runtimes within 30 seconds.
  • A data share holds one read grant per table, view or semantic model. A receiving team never gets administration; an external secret is shown once, never stored.
  • MCP accepts only tokens issued to the iceberg-mcp client, verified on every call: an agent never holds more than its user.
  • Extensions get no secrets or storage keys: a team's service account, enabled by its administrators and revocable by the platform administrator.
This build is meant for local development. HTTPS, persistent sessions and hostile-tenant isolation are on the roadmap, and the boundaries are documented.

03 · Demo · Semantic model with your coding agent

The agent looks at the data, asks the owner, and proposes a model

1 · Profile: what is in the data

The agent counts and measures every column of the 32,256 readings. That shows what is odd, not what it means:

  • 1,920.6 kW on cables rated at most 680 kW
  • negative load down to -417.6 kW
  • a cable temperature of -999 °C
  • 24 quarter-hours without any data
2 · Interview: what it means

First the questions the model must answer; sander gives six, such as “Which feeders ran above their rating last week?” Then the meaning, a few questions at a time:

agent

Which readings count?

sander

OK and ESTIMATED. SUSPECT failed the plausibility check.

agent

And negative load?

sander

Solar feed-in. We call it teruglevering.

3 · Proposal: a draft model

The agent writes the answers down as a semantic model and plays it back before anything is stored:

  • overload_hours: valid quarter-hours above the rating, divided by 4
  • SUSPECT and MISSING never count in a load metric
  • -999 means a broken sensor
  • teruglevering and overbelasting as synonyms
In short: the data shows what is odd, only the team knows what it means. The agent asks, the team decides.
Real profile output from the semantic-model skill, shortened; sander's answers were written for the demo. The skill ships with the installer in .agents/skills, in the open Agent Skills format, so Claude Code, Codex, GitHub Copilot and others pick it up. Its steps: connect, scope, profile, interview, draft, check, review, publish. The rule it follows: never guess business meaning. The data can suggest an answer, the owner confirms it. It asks at most four questions per round, each with its own suggestion where the profile supports one. One suggestion was wrong for this domain: it proposed a signed average utilisation, but a cable heats up from feed-in as much as from demand, so the metric uses the absolute value. That is exactly the knowledge that is not in the data. Owner (grid-planning), refresh (daily SCADA export at 06:00 UTC) and classification (internal, no personal data) are asked too. The full transcript and the work files are in presentation/grid.

Grain and keys

One row per feeder per quarter-hour, and a key per dataset, so the agent knows what it counts.

Relationships

FEEDER_LOAD → FEEDER → SUBSTATION. Ossie points a relationship from the many side to the one side; the platform only joins that way, so no reading is counted twice.

Metrics

Seven, each defined once with its exclusions and unit. "Last week" is a filter, not a metric.

AI context

UTC days, the quality codes, owner and refresh, the synonyms from the interview, and how to answer.

Apache Ossie semantic model, shortened · Ossie describes, it does not run anything · Polaris stores it beside the tables, the platform compiles the queries
SM draft writes one dataset per table and one field per column, with TODO wherever meaning is needed; the agent fills those in from the interview. The full document is presentation/grid/semantic-models/grid_sensors/feeder_load.json, and the Definition tab in the catalog shows the stored version. Division of labour: the Ossie specification defines a relationship as from the many side (from) to the one side (to), with to_columns the primary or unique key of the one side. Ossie itself executes nothing. The platform's governed-query compiler joins only along that direction and only onto a primary key, so every join is many-to-one and a metric is never inflated; a question that would fan out is refused (user_portal/semantic/compiler.py). Governed queries accept only an allowlist of SQL: aggregates and scalar functions over the model's own columns, no subqueries, no table functions. That is why time windows are filters at question time rather than metrics.

03 · Demo · Data sharing

Share the model with another team, without a copy

mila administers grid-planning · the feeder_load model for outage-response · its three tables come alongnoor in outage-response · only the shared objects, read-only, owner named
A team administrator picks tables, views and semantic models of one database and chooses the recipient: another team, an external party, or both. Selecting a model selects the tables it reads, because a model without its tables cannot be queried. In Polaris a share is one catalog role with one read grant per object, nothing on the namespace or catalog, so a recipient cannot list anything else. A team share is granted to each member's own principal role, including people who join later, and removed when they leave. An external party gets a client ID and a secret shown once, and loads the model by its address with any Iceberg REST client. Shares can expire and be revoked at any time; the platform administrator sees every share and can revoke it. There is still only one copy of the data.

Wrap up

As far as I'm concerned

  • Iceberg complements platforms like Snowflake. Use it where openness pays off: data that several teams, engines or partners read. Not every table needs to be an Iceberg table.
  • Combining data products is where an integrated platform wins. Joining many data products in one place with good performance is easier when storage, compute and catalog come from one vendor.
  • For Iceberg tables, engines are replaceable. My advice is to treat them as workload decisions, not as platform commitments.
  • Meaning belongs next to the data. A semantic model is part of the data product: owned by the team, checked before it is published, and shared and governed like the tables.
  • Self-service only works with clear ownership. Teams create, own and share their databases, while the platform team owns the building blocks.
  • Agents use the same front door. They get the same identity and grants as the people they work for.
  • Keep the core small, grow through extensions. New capabilities such as Conversational BI come with their own release, behind one versioned contract.
