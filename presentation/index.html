Intro · How I build

Five principles behind every choice

1 · Clean UXNo ticket, no manual. From sign-in to a notebook in a few clicks, one design language in both portals, and a Getting started page in each.
2 · API firstThe portal is just a client. Every button is a documented route with an OpenAPI schema, so a script can do everything a person can.
3 · AI nativeAgents are first-class users. Both portals serve MCP with the user's own identity, data products carry their meaning in a semantic model, and agent skills ship with the installer.
4 · Open sourceNothing to rent. Every building block is Apache-2.0 or MIT, and so is the platform. No vendor account and no trial clock.
5 · Loosely coupledOpen interfaces between the blocks. Iceberg REST, S3, OIDC and MCP, so you can replace one block without touching the others.

These principles decide the trade-offs. When a feature does not fit them, it does not go in.

This is the lens for the rest of the talk. Clean UX: team members serve themselves; destructive actions ask for the exact name. API first: the UI has no private backdoor, the OpenAPI schema comes from the same code. AI native: MCP on both portals, tokens issued to the iceberg-mcp client, and two skills in the Agent Skills format in the installation folder. Loosely coupled: every connection between building blocks is an open standard, which is what makes swapping possible.

The one-liner

Apache Iceberg is doing for data what open APIs did for applications.

REST and OpenAPI made it possible for any service to talk to any application. Apache Iceberg does the same for structured data: one open table standard, so no single engine owns your data.

01

How Apache Iceberg works

And why it is not a database platform like Snowflake.

01 · Iceberg

Iceberg is a specification, not a product you buy

Snowflake · Databricks · BigQuery
  • One vendor delivers storage, compute, catalog, security and the UI as a single product.
  • Your tables live in the vendor's format and in the vendor's account.
  • You rent the capability, so leaving means migrating the data and everything built around it.
Apache Iceberg
  • An open specification for how table data and metadata are laid out in object storage.
  • Data files are plain Parquet and metadata is JSON and Avro, so no server owns them.
  • You bring the catalog, the engines, the storage and the identity provider, and each one stays replaceable.

The point of the comparison is ownership: which parts of the stack you control yourself, and which parts you rent.

01 · Iceberg

Start with what you already know: PostgreSQL

Imagine a simple table: columns, rows and SQL queries.

Who does the job?A regular PostgreSQL tableAn Iceberg table in this platform
Run your SQLThe PostgreSQL server.An engine such as DuckDB or Spark.
Find the table
and check access		PostgreSQL's system catalogs and permissions.Polaris: the table's name, permissions and current metadata location.
Describe the columnsPostgreSQL's system catalogs.An Iceberg metadata file in object storage.
Store the rowsFiles managed and read by PostgreSQL.Parquet files in a bucket, read directly by the engine.

PostgreSQL brings these jobs together. With Iceberg, you choose the components separately.

Compare responsibilities, not identical internals. PostgreSQL also stores data in files; applications normally access those files through its server. For an Iceberg query, the engine asks Polaris for the table metadata and access, then reads table files directly from storage. Polaris can read and write Iceberg metadata during catalog operations, but query rows do not flow through it. Even when Polaris uses PostgreSQL as its backing store, that database holds catalog records and permissions; the Iceberg schema and snapshot history live in object storage. Sources: PostgreSQL architecture, PostgreSQL system catalogs, Polaris 1.8.0 entities, Polaris 1.8.0 vended credentials, Polaris 1.8.0 JDBC metastore. Background reading: The Architecture of Apache Polaris, Under the Hood.
01 · Iceberg
↓ see the files

From a table name to its rows

The engine follows a chain of references. Each step answers one question.

1 · CatalogPolarisWhere do I start? Checks access and points to the current metadata file.
2 · Table descriptionmetadata.json · in the bucketWhat does this table look like? Its columns and saved versions, called snapshots.
3 · Lists of filesmanifest list → manifests · in the bucketWhich files belong to this snapshot? File lists and statistics help the engine choose what to read.
4 · The rowsParquet files · in the bucketWhat are the values? The actual flights your query uses.

A bucket can also contain old or unused files. The references define the table.

Read down the chain once, without asking the audience to remember file extensions. Step 3 groups two levels: a snapshot points to a manifest list, which points to manifests; manifests track data files and, where relevant, delete files. Their statistics help skip files that cannot match a query. These are file inventories, not PostgreSQL B-tree indexes. Parquet is the data format used in this demo. Polaris keeps the current metadata location in its catalog state; everything below that reference is in object storage. Source: Iceberg specification: overview. 01 · Iceberg

How a new batch becomes visible

Imagine adding today's flights. Readers should see the whole batch together.

1 · Prepare

Write new files

The writer adds the new rows and file lists to storage. The current table still points to the previous version.

2 · Commit

Publish the new version

New table metadata is written. Polaris checks the commit and atomically switches the current metadata reference.

3 · Read

See a complete snapshot

New queries can see the batch. Queries already reading an older snapshot keep a consistent view.

If another writer commits first, the change must be rechecked and retried or rejected.

The familiar PostgreSQL idea is COMMIT making a transaction visible. Here, the atomic publication described is for one Iceberg table; do not imply a PostgreSQL-style transaction across several tables. The catalog checks the expected prior state. Uploading a Parquet file alone does not add it to the table. Unchanged files can be reused by the new snapshot. Snapshot expiry must leave running readers enough time to finish. Source: Iceberg reliability and concurrent writes.
01 · Iceberg

What this means when you use the table

You want to…A regular PostgreSQL tableAn Iceberg table
Publish a batch safelyCommit a transaction; it can span several tables.Publish one table version atomically through the catalog.
Rename a columnChange the column definition with ALTER TABLE.Update metadata; the column ID stays the same and data files stay in place.
Read an earlier versionUsually needs history tables or a backup restore.Choose an older snapshot, while its metadata and files are retained.
Use another engineOther tools normally query through PostgreSQL.Compatible engines read the same table files directly.

Iceberg defines the table rules. Engines and catalogs implement them; feature support varies.

Lead with familiar outcomes, rather than an inventory of every Iceberg feature. PostgreSQL MVCC provides consistent transaction views, not a built-in SQL interface to query arbitrary historical table versions. Iceberg time travel depends on retaining snapshots and their files. Metadata statistics and hidden partitioning also help engines avoid unnecessary reads; partition layouts can evolve without rewriting existing files. Branches, tags and v3 features such as deletion vectors are useful follow-up topics. Views have a separate specification and are catalog objects, not a feature of the table's data files. Iceberg does not by itself provide PostgreSQL's primary-key or foreign-key enforcement. Sources: Iceberg evolution, Iceberg reliability.
01 · Iceberg

What Iceberg is not

  • It is not a query engine and does not execute SQL, so you pick DuckDB, Trino, Spark, Snowflake, or all of them.
  • It is not a storage system: it sits on the S3 compatible object storage you already have.
  • It is not a security layer by itself. Permissions and credential vending live in the catalog and in your identity provider.
  • It is not maintenance free. Compaction, snapshot expiry and orphan cleanup are yours to schedule.

That separation is deliberate: because the building blocks are independent, you decide who owns each one.

02 · Open source

What avoiding lock-in means in practice

Data

The data is Parquet in a bucket you control. Moving means copying the bucket and pointing another catalog at it, without an export job or a negotiation about egress.

Catalog

Iceberg REST is an open API, so Polaris today can be another REST catalog tomorrow. The table metadata already lives next to the data.

Engines

Whether a team runs local analysis with DuckDB, distributed queries on Trino, or Snowflake where that is justified, every engine points at the same dataset without duplication.

Vendor lock-in rarely happens overnight; it creeps in through the default choices. Open formats keep the platform flexible and save us a costly migration later.

Autonomy

  • A one command installer for Linux, macOS and Windows, without a vendor account or a trial clock.
  • You decide where the data lives and which network it ever touches.
  • The cost is compute and storage you already pay for.
Portability
  • Storage: anything with an S3 API.
  • Identity: any OIDC provider, with users and roles staying yours.
  • Catalog: any Iceberg REST implementation.
  • Compute: whichever engine fits the job, per team and per workload.

02 · Open source

PS: the honest part

  • Operations are your responsibility: upgrades, backups of Postgres and the buckets, monitoring, HTTPS and secrets.
  • Table maintenance is yours as well. Compaction, snapshot expiration and orphan file cleanup need a schedule.
  • Security boundaries are explicit. This build is a local development platform with in-memory sessions on a trusted Docker host, so read the security model before running it anywhere else.
  • Fewer vendors means tighter control over the architecture, but we have to be realistic: it also pushes more integration decisions onto a small team.
  • Performance across data products is harder. Combining many Iceberg data products and querying them fast takes more work than inside one integrated platform.

Open source does not mean free of work. The ownership you gain comes with the responsibility that goes with it.

03 · Platform

The capability model

  • A team owns databases and has a stable ID, a unique name and a description.
  • A user signs in with Keycloak, belongs to one or more teams and has a role per team: read, read and write, or admin.
  • A database is an Iceberg catalog in Polaris plus a dedicated S3 bucket. Team administrators create, rename and delete their own.
  • Every database has an environment: development, acceptance or production.
  • A data share gives another team, an external party, or both read access to selected tables, views and semantic models of one database.
  • A semantic model sits next to the tables in a namespace and says what they mean: datasets, joins and agreed metrics.
  • Effective access is the union of the user's teams, each at its own role. Moving a database re-syncs grants and bucket policies.
  • A team share follows membership: join the receiving team and you can read it, leave and you cannot.
  • There is no second application database: Polaris is the source of truth for teams, users and catalogs.
  • Portal administration is a Keycloak role; administering a team does not grant it.

Ownership is explicit: a team owns a database and a database owns a bucket. That is the governance model.

Polaris RBAC, filled in by the demo-company skill

Left is the Polaris model from the 1.8 access-control docs: privileges are granted to catalog roles, catalog roles to principal roles, principal roles to principals. Right is what the demo-company skill leaves behind for 12 participants on a fresh install; seats go round-robin, so grid-planning gets pool entries 1, 4, 7 and 10. The twist: the platform gives every user a personal principal role (create_user) and grants catalog roles to that, per catalog the team owns (sync_access). A team is also a principal role (save_team), but only as a record: nobody is granted it. Membership lives in the portal.memberships property and is turned into grants whenever it changes. Every database gets reader, writer and admin catalog roles (create_database). Participants are admin or writer; the skill links the trainer's own platform-admin account as a platform user with reader in every team (link_user), because portal administration grants no data access. Reader holds 10 list and read privileges, including SEMANTIC_MODEL_LIST and SEMANTIC_MODEL_READ. CATALOG_MANAGE_CONTENT already includes MANAGE_METADATA and table read and write, so in Polaris terms admin adds MANAGE_ACCESS. Creating databases and data shares as team admin is checked by the user portal, not by a Polaris privilege. platform-admin is a Keycloak role; the admin portal and its MCP server then act as Polaris service_admin.
03 · Platform · After the skill

Data shares in Polaris terms: one catalog role, two ways in

One share is three Polaris records named share-…: a catalog role, a principal role and a principal · to a team, an external party or both · selecting the model selects the tables it reads · a team admin creates it, in the portal or through MCP
Same example as the data sharing demo later on: the grid-planning admin shares the flights semantic model with outage-response and with a research partner. Selecting the model selects the six tables it reads, because a model without its tables cannot be queried. create_share makes the catalog role with exactly one grant per object, TABLE_READ_DATA for a table, VIEW_READ_PROPERTIES for a view or SEMANTIC_MODEL_READ for a semantic model, and nothing on the namespace or catalog, so nobody can list. An external recipient loads the model with a GET on its address under the Polaris API, using a token from the token endpoint. For the team, sync_team_shares grants that catalog role to each member's personal principal role, including people who join later, and removes it when they leave. The share principal of a team-only share never receives its principal role, so its secret opens nothing. For an external share, assigning the principal role to the principal is the very last step, after every check. New secret resets the principal: same client ID, the old secret dies at once. Revocation unassigns the external role first, then removes members' grants, the catalog role, the principal role and the principal. Storage credentials that were already vended stay valid until they expire.

Team share versus external share

Team shareExternal share
Who readsEvery member of outage-response, now and in futureA research partner, or any party outside the platform
IdentityTheir own Keycloak accountsA share-… client ID and secret
Grant pathShare catalog role → each member's personal principal roleShare catalog role → share principal role → share principal
WhereUser portal, notebooks, their own tools and AI agentsDuckDB, PyIceberg or any other Iceberg REST client · a model with a GET on its address
CredentialNothing to hand outShown once and never stored · New secret keeps the client ID and ends the old one at once
Expiry and revokeOptional expiry, enforced every 30 seconds · revoking ends Polaris tokens and team grants at once · storage credentials already vended expire on their own
LimitsAt least one table and at most 50 objects per share, 20 shares per database · recipients fixed at creation · managed by the owning team's administrators; the platform administrator can only revoke

One share can do both, because both paths end in the same catalog role.

The team share is the internal route: nothing leaves the platform, and access is re-checked against Polaris on every request, so leaving outage-response ends it. The external share is the only way a credential leaves the platform; treat the secret like a password. A shared view is a definition, not a filter: the tables it reads are shared with it. A shared database cannot move to another team until its shares are revoked, so a new owner never inherits access it did not grant. Sources: create_share, sync_team_shares, rotate_share and delete_share in server/polaris.py, and SECURITY.md.

Demo · AI-ready data

A data product is data, meaning, evidence and access

Data

Six Iceberg tables in ai_flights: 12,000 synthetic flights with their airports, carriers, aircraft, routes and runways. DuckDB generates and writes every row with SQL.

Meaning

A semantic model in the same namespace: 6 datasets, 7 relationships, 4 agreed metrics and instructions for AI.

Evidence

11 SQL checks on keys, joins, coordinates, time order and cancellations. One failure and nothing is published.

Access

Polaris decides who reads the tables and the model: team roles, and data shares. An agent gets exactly the grants of its user.

Tables alone are not AI-ready. An agent also needs to know what a row means, which metric is agreed and whether the data passed its checks.

The notebook opens with the same line: a useful data product combines data, meaning, quality evidence and access. The data is synthetic, with no real flights or passenger data. The concepts come from the Apache Ossie flights example; a small product contract beside the notebook adds the grain, units, null policy, metrics and quality checks. After publication, readers need neither file: everything lives in Polaris.

Demo · Data sharing

Share with another team or someone outside, without a copy

01 · Team administrator

A team administrator picks tables, views and semantic models of one database and chooses the recipient: another team, an external party, or both. Selecting a model selects the tables it reads.

02 · Polaris

Access is granted per object: an explicit read grant for each selected table or view, rather than blanket permissions on the namespace or the catalog.

03 · Recipient

Members of the receiving team use their own accounts, in the portal, notebooks and agents. An external party uses any Iceberg REST client, and loads a model by its address.

Every recipient reads the same files and the same meaning, and the team can expire or revoke access at any time. There is still only one copy of the data.

This is the open-standard answer to vendor data sharing: the contract is Iceberg REST plus S3, so the recipient can bring an engine of choice. Ownership stays with the team that owns the database, and every administrator of that team manages the same shares. A team share is granted to each member's own Polaris role, including future members, and removed when a member leaves. Destinations are fixed when the share is created. A shared model without its tables cannot be queried, so the portal adds them and the API warns about any that are missing.

What an external recipient can and cannot do

catalog = load_catalog(
    "shared", type="rest", uri=URI, warehouse="db-…",
    credential=f"{ID}:{SECRET}", scope="PRINCIPAL_ROLE:ALL",
    **{"header.X-Iceberg-Access-Delegation":
       "vended-credentials"},
)
catalog.load_table("ai_flights.flights").scan().to_arrow()
                                        # 12,000 rows

# The model: a GET on the address shown with the credential
token = httpx.post(URI + "/v1/oauth/tokens", data={
    "grant_type": "client_credentials", "client_id": ID,
    "client_secret": SECRET, "scope": "PRINCIPAL_ROLE:ALL",
}).json()["access_token"]
httpx.get(MODEL_URL, headers={"Authorization": f"Bearer {token}"})
                                        # 200

catalog.list_namespaces()               # Forbidden
catalog.load_table("ai_flights.other")  # Forbidden
httpx.get(MODELS_URL, headers=…)        # Forbidden: no listing
  • A share holds no list privilege, so the recipient loads only the shared objects: tables by full name, a model by its address.
  • Storage follows the grant: vended S3 credentials are read-only and stop at the prefix of the shared table.
  • A model or a view is a definition rather than a filter, so the tables it reads are shared with it and readable in full.
  • Revoking is immediate for catalog tokens; storage credentials already handed out expire on their own.
  • Outside one machine this needs your own TLS proxy in front of Polaris and RustFS.

03 · Platform

Security model, in one slide

  • The user portal, Polaris, the notebooks and MCP all work with that user's Keycloak token. No shared service account for data access.
  • Polaris vends short lived, table scoped S3 credentials; notebooks never see bucket root keys.
  • Each notebook session gets its own container and network: read-only root filesystem, dropped capabilities, CPU, memory and process limits, no Docker socket.
  • Revoking a membership stops the affected runtimes within 30 seconds.
  • A data share holds one read grant per table, view or semantic model. A receiving team never gets administration; an external secret is shown once, never stored.
  • MCP accepts only tokens issued to the iceberg-mcp client, verified on every call: an agent never holds more than its user.

This build is meant for local development. HTTPS, persistent sessions and hostile-tenant isolation are on the roadmap, and the boundaries are documented.

What this means for us

Direction and ownership.

04 · Wrap up

As far as I'm concerned

  • Iceberg complements platforms like Snowflake. Use it where openness pays off: data that several teams, engines or partners read. Not every table needs to be an Iceberg table.
  • Combining data products is where an integrated platform wins. Joining many data products in one place with good performance is easier when storage, compute and catalog come from one vendor.
  • For Iceberg tables, engines are replaceable. My recommendation is to treat them as workload decisions and not as platform commitments.
  • Meaning belongs next to the data. A semantic model is part of the data product: owned by the team, checked before it is published, and shared and governed like the tables.
  • Self-service only works with clear ownership. Teams create, own and share their databases, while the platform team owns the building blocks.
  • Agents use the same front door. They get the same identity and grants as the people they work for.
